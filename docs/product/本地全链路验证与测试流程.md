## 1. 配置说明（重点：LLM / 环境变量）

- **配置读取方式**：factory-agent 只读取**进程环境变量**（pydantic-settings，前缀 `FACTORY_AGENT_`），
  **不会自动读取仓库根 `.env`**。mock-mes 才会自动读取根 `.env`（前缀 `MOCK_MES_`）。
- **LLM Key**：模型部署在 `configs/knowledge/models.yaml` 登记，逻辑别名
  `factory-fast / factory-reasoning / factory-summary` 全部指向 DeepSeek OpenAI 兼容接口
  （`https://api.deepseek.com/v1`），Key 的环境变量名为：

  ```bash
  export FACTORY_AGENT_LLM_KEY_DEEPSEEK='sk-你的key'
  ```

  未配置该 Key 时 `/health/ready` 的 `model` 为 `not_configured`，问答（意图解析）不可用；
  其余服务仍可启动。
- **推荐做法**：把 `FACTORY_AGENT_*`（含 Key）追加到仓库根 `.env`（git 已忽略）便于统一管理，
  启动前执行：

  ```bash
  set -a; source .env; set +a
  ```

  （或直接 export；用 docker compose 时 .env 会被自动注入，无需 source。）

## 2. 环境准备

- Python 3.12 + uv；Docker + Docker Compose（本地 Postgres）。
- 安装依赖（首次）：

  ```bash
  make bootstrap          # uv sync --all-packages --group dev
  ```

- 需要时启动本地中间件（Postgres/Redis；本手册 Postgres 必需，Redis 可选）：

  ```bash
  docker compose -f deploy/compose/compose.yaml up -d postgres   # 127.0.0.1:3432
  # 可选：docker compose -f deploy/compose/compose.yaml up -d redis
  ```

- **根 `.env`（git-ignored）**：至少包含（本地开发口令，见 deploy/compose/postgres/init-databases.sql）：

  ```bash
  MOCK_MES_DATABASE_URL=postgresql://mock_mes:mock_mes_dev@127.0.0.1:3432/mock_mes
  MOCK_MES_TEST_DATABASE_URL=postgresql://mock_mes:mock_mes_dev@127.0.0.1:3432/mock_mes_test
  FACTORY_AGENT_POSTGRES_URL=postgresql://factory_agent:factory_agent_dev@127.0.0.1:3432/factory_agent
  FACTORY_AGENT_LLM_KEY_DEEPSEEK=sk-...
  ```

### 4.2 起 factory-agent（终端 B，端口 8000）


`/health/ready` 期望（问答可用的前置）：

| 依赖 | 期望 | 说明 |
| --- | --- | --- |
| identity | configured | 配了 canonical_mes_base_url 即有 token 网关 |
| mes | configured | 同上 |
| model / litellm | configured | 必须有 FACTORY_AGENT_LLM_KEY_DEEPSEEK |
| interactions / postgres | configured | 必须有 FACTORY_AGENT_POSTGRES_URL |
| redis / sessions / artifacts / export | 可 not_configured | 仅缓存/导出，不影响问答 |

### 4.3 身份与角色（重要）

- API 边界只认请求头 `X-Factory-Credential: <加密 app_key>`；factory-agent 用它到
  `/api/system/token` 换 bundle。Mock 下传 `APPKEY-A` 会换成**该租户老板**（01009，role 99）。
- 因此本地自然语言验证默认以**老板视角**进行：可问全厂类（FR-008/009/010/011）与任一员工
  （FR-012）。员工/组长/管理的四角色数据范围，用自动化测试矩阵覆盖（见 §5）。
- 角色矩阵外的问题会被友好拒绝并提示可查范围（非裸 403）。

### 4.4 发起一次问答（员工工资示例）

```bash
# (1) 创建 interaction
curl -s -X POST http://127.0.0.1:8000/v1/sessions/demo-001/interactions \
  -H 'Content-Type: application/json' \
  -H 'X-Factory-Credential: APPKEY-A' \
  -d '{"text":"查一下员工 01001 上个月的工资"}'
# => {"interaction_id":"<id>","session_id":"demo-001","status":"pending",...}

# (2) 拉 SSE 结果流（把 <id> 换成上面返回值）
curl -N http://127.0.0.1:8000/v1/interactions/<id>/stream \
  -H 'X-Factory-Credential: APPKEY-A'
# 期望：interaction.started → phase → result（含工资数字）→ completed

# (3) 事后查该会话历史消息
curl -s http://127.0.0.1:8000/v1/sessions/demo-001/messages \
  -H 'X-Factory-Credential: APPKEY-A'
```

### 4.5 建议验证问题清单（老板视角 + 口径检查）

| 目的 | 问法（示例） | 预期 |
| --- | --- | --- |
| FR-012 任一员工工资 | `查一下员工 01001 上个月的工资` | result 含该员工工资合计（GongziMx 汇总） |
| FR-011 全厂工资（在册/人均） | `全厂上个月工资统计` | 按车间/小组分行：应发合计、在册人数、人均工资 |
| FR-008 工资清单 | `上个月全厂工资清单` | 按 je 倒序的排名清单 |
| FR-009 交期预警字段 | `这个月各订单进度` | 输出含 `delivery_warning`（1/0）与 `days_remaining` |
| 时间上限友好拒绝 | `2025年全年的工资`（>366 天） | 友好提示“时间范围超出上限（近一年）”，零 MES 调用 |
| 角色矩阵外友好拒绝 | 老板以外角色问 FR-011（需先以该角色登录） | 提示可查范围，非 403 |

**注意事项**
- `01001` 与 `01002` 都叫「模拟员工甲」：**只按姓名问会命中同名未定 uid → 友好拒绝（零业务调用）**。
  用“工号 + 时间”最稳；或问唯一姓名员工。此同名口径是 Story 1 有意保留的边界。
- 时间范围建议落在数据窗口内（本地生成了 2026-07-01 ~ 2026-08-21，虚拟今天 2026-08-21），
  用“上个月/这个月”即可；跨出窗口（如更早月份）会返回空/无数据，不算错误。

### 4.6 常见故障排查

| 现象 | 原因/处理 |
| --- | --- |
| `/health/ready` model=not_configured | 未配 `FACTORY_AGENT_LLM_KEY_DEEPSEEK` |
| 401 credential was rejected | `X-Factory-Credential` 头缺失/取值不被 Mock 识别（应含 `APPKEY-A` 或后缀 A） |
| 502 token exchange unavailable | Mock 未启动或 `FACTORY_AGENT_CANONICAL_MES_BASE_URL` 不对 |
| 交互无 result 只有澄清 | 问法缺时间/员工等槽位；补齐后再问 |
| 结果为空 | 时间窗口内该员工无数据；换 01003+ 等有产出的员工或换月份 |
| 同名员工被拒 | 用工号或加车间限定，避免“模拟员工甲”歧义 |
| loguru 只打 JSON 日志难读 | 启动时 `export FACTORY_AGENT_LOG_FORMAT=console` |
