## 4. 手把手：Debug 一次问答（Factory Agent 主链路）

问答的"一次交互"拆成**两个 HTTP 动作**，这是理解整个系统的关键：

```
POST /v1/sessions/{sid}/interactions          ← ① 只落库：记 PENDING + 用户消息，立即返回
        ↓
GET  /v1/interactions/{id}/stream  (SSE)      ← ② 谁先连上谁执行：claim_run 抢占 → 跑完整 pipeline
        ↓                                          （断线重连只重放已持久化事件，不会重复调 MES）
SSE 帧: interaction.started → phase… → result/completed  （每帧同时落库）
```

**建议先下断点的 5 个位置**（从外到内排查）：

1. `src/factory_agent/api/sessions.py:94` `start_interaction()` —— 请求是否进来、身份是否解析成功。
2. `src/factory_agent/application/session.py:251` `SessionService.stream()` —— SSE 是否被消费、claim 抢占是否成功。
3. `src/factory_agent/application/session.py:395` `_pipeline()` —— **核心编排**：意图解析→授权→过滤→执行→落库。
4. `src/factory_agent/application/session.py:673` `_parse()` → `src/factory_agent/application/intent.py:139`
   `CapabilityIntentParser` —— LLM 把问题解析成 capability+槽位的地方（"没识别对"就看这里）。
5. `src/factory_agent/execution/kernel.py:89` `KernelCapabilityRunner.run` —— recipe 真正取数/计算的地方（"结果不对"看这里）。

不打断点、只想看全链路日志：8081 页面问一句，后端 console 会按 stage 打日志；
想看 JSON 之外的日志格式，可在 `.env` 或 launch `env` 里加 `FACTORY_AGENT_LOG_FORMAT=console`。

### 5.2 Agent 处理起点与整体逻辑（一次问答完整链路）

**处理起点**不在某一行，而是「POST 落库 + SSE 抢执行」两段式；**真正的 Agent 逻辑集中在
`application/session.py` 的 `_pipeline()`**。整条链路按顺序：

| # | 环节 | 文件:函数（行号快照 2026-09-04） | 说明 |
| --- | --- | --- | --- |
| 1 | HTTP 入口 | `api/sessions.py` `start_interaction`(:94) | 校验身份（`api/identity.py`，凭据→token 网关换 bundle→角色+数据范围）后只落库 PENDING |
| 2 | 执行起点 | `application/session.py` `stream`(:251) → `_run`(:339) | SSE 连接到达，`claim_run` CAS 抢占；发 `interaction.started` |

| 6 | 授权 | `application/permission_matrix.py` `authorize_capability`(:107) | 角色×能力矩阵判定（00/01/02/99），拒绝走友好提示 |

## 6. 常见故障排查（debug 视角）

| 现象 | 先查什么 |
| --- | --- |
| F5 启动报端口被占用 | 上一轮没停干净：`lsof -nP -iTCP:8000 -sTCP:LISTEN` 找到 PID kill 掉，或 Debug 面板停掉旧实例 |
| `/health/ready` 的 model=not_configured | `.env` 缺 `FACTORY_AGENT_LLM_KEY_DEEPSEEK`（或 LAUNCH envFile 没加载）；改 .env 后要**重启**（envFile 只在启动时读一次） |
| 401 `credential header is missing / rejected` | `X-Factory-Credential` 头缺失/不被 MES 识别。8081 页面出这个 → 检查 `.env` 的 `MES_APP_KEY_0x`；curl 出这个 → 头没带对 |
| 502 token exchange unavailable | MES 根地址连不上：`FACTORY_AGENT_CANONICAL_MES_BASE_URL` 指向客户机但没连 VPN/内网，或指向 8010 但 mock-mes 没起 |
| 问答只有澄清、没有结果 | 问法缺槽位（时间/款号/员工…）；补齐再问 |
| 结果 0 行/空 | 时间窗内无数据；或角色范围本来就看不到（员工问全厂 = 空/拒绝） |
| 单测突然全红 / 出现诡异 401 | **litellm import 会自动加载仓库根 .env 到 os.environ**，污染 `FactoryAgentSettings(environment=test)`。已修：`tests/conftest.py` 顶层注入后清掉 `FACTORY_AGENT_*`。若再出现，优先查是不是又新增了 import litellm 的路径 |
| 改了 Python 代码但行为没变 | uvicorn 无 reload：重启 debug 实例；确认 VS Code 断点命中在最新代码（看文件 mtime/行号） |
| 改了前端代码但没变化 | 8081/8082 已 no-store，硬刷新（Cmd+Shift+R）；确认代理指向的 upstream 端口对（`.env` 的 `FA_FE_UPSTREAM`/`UA_DEMO_UPSTREAM`） |
| loguru 日志挤成 JSON 难读 | `FACTORY_AGENT_LOG_FORMAT=console` |
| `UndefinedTable: relation "agent_message" does not exist` | **factory_agent 库没跑过 factory-agent 迁移**（连 `alembic_version` 表都没有 = 从未 migrate）。跑：`set -a; source .env; set +a` 后 `.venv/bin/python -m factory_agent.persistence.migrations upgrade head` |
| `UndefinedTable: relation "tenant_registry" does not exist` | **usage_admin 迁移没跑**（表 owner=usage_admin，与 factory-agent 同库）。跑：同上 source 后 `.venv/bin/python -m usage_admin.migrations upgrade head` |
| 迁移报 `permission denied for schema public` | 旧 volume 首次 init 时缺授权。一次性补：`docker exec factory-agent-middleware-postgres-1 psql -U postgres -d factory_agent -c "GRANT CREATE ON SCHEMA public TO usage_admin;"`（详见 §7） |
| 迁移报 `USAGE_ADMIN_DATABASE_URL is required` | usage-admin 的 settings **不自动读 .env**，终端跑必须先 `set -a; source .env; set +a`（VS Code launch.json 的 envFile 会自动注入，不用手动） |

## 7. 库迁移与造数（首次 / 换库 / 报 UndefinedTable 时做）

> 判定当前该跑哪套迁移：`docker exec factory-agent-middleware-postgres-1 psql -U postgres -d factory_agent -tAc "SELECT version_num FROM alembic_version;"`
> - 该表**不存在** → factory-agent 迁移从没跑过，跑下面第 2 条。
> - 查 `alembic_version_usage_admin` **不存在** → usage-admin 迁移没跑过，跑第 3 条。
>
> factory-agent 与 usage-admin **共库不同 owner**（都连 `factory_agent` 库，表归属各自主，互读靠 GRANT）：
> - factory_agent owner 表：`agent_interaction` / `agent_message` / `interaction_fact` / `usage_event*` 等（20 张）
> - usage_admin owner 表：`tenant_registry` / `platform_principal` / `usage_export` / `admin_audit`（4 张）

```bash
make middleware-up                       # 先起 postgres
set -a; source .env; set +a              # 必须：两个 -m 迁移入口都不自动读 .env

# mock_mes 库（8010 服务读取；短窗口即可，全窗口加 --fill-missing）
uv run --package mock-mes mock-mes-migrate upgrade head
uv run --package mock-mes mock-mes-generate --start 2026-07-01 --end 2026-08-21

# factory_agent 业务库（agent_* 表，owner=factory_agent）
.venv/bin/python -m factory_agent.persistence.migrations upgrade head

# usage_admin 运营库（tenant_registry 等 4 张表，owner=usage_admin）
.venv/bin/python -m usage_admin.migrations upgrade head
```

> 若旧 volume 上迁移报 `permission denied for schema public`（usage_admin 无建表权），一次性补授权后重跑：
> ```bash
> docker exec factory-agent-middleware-postgres-1 psql -U postgres -d factory_agent \
>   -c "GRANT CREATE ON SCHEMA public TO usage_admin;"
> ```
> 跨服务互读（ADR-0003：factory-agent 启动时读 tenant_registry 做 D13 前置校验；usage-admin 读 usage_event 计量）。新表默认不自动授权，跑完迁移补一次：
> ```bash
> docker exec factory-agent-middleware-postgres-1 psql -U postgres -d factory_agent \
>   -c "GRANT SELECT ON ALL TABLES IN SCHEMA public TO usage_admin; GRANT SELECT ON ALL TABLES IN SCHEMA public TO factory_agent;"
> ```

> docker volume 保留策略：`make middleware-down` / `docker compose ... down` **不带 -v** 时数据都在，
> 重启容器即回到上次状态，无需重新 migrate/造数（表与数据都保留；但换机器 / 删 volume 后必须整段重跑）。
