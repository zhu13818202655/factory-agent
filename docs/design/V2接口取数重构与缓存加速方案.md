# V2 接口取数重构与全厂明细缓存加速方案

> 状态：当前确认方案 ｜ 更新：2026-10-13
>
> 决策见 ADR-0010。本文定义当前实现和验收口径；本地合成测试不能替代客户逐组等价、真实权限
> 与容量测量。本文不声明客户验收、生产上线或固定耗时收益已经完成。

## 1. 目标与范围

FR-001～FR-013 及其已支持的列表、包级、工序级下钻都使用公共业务明细缓存。
每个已授权工厂只有工资产量与生产进度两族底料，角色、员工、部门、订单、款号和展示分组
在读取时派生。目录与在册人数使用独立安全名册缓存。功能输出、角色矩阵及下钻的新一轮问答形态保持。

“全部利用缓存”指每个分支都接入并可命中；冷态、过期、故障或一致性失败仍允许实时回源。
热态历史底料、相关目录已预热且非 shadow 时，业务 MES 调用数应为零。
LLM 调用、token 换取/续期、统计 API、部署环境和新业务能力不属于本次缓存契约的扩展范围。

## 3. 统一底料与计算口径

### 3.1 默认明细契约

工资产量 `GongziClQuery` 不传 `groupbyFields`，现有业务统一 `Flag=0`、`Type=0,1,2`。
明细保留员工、部门、日期、计划号、款号、工序、单价、数量和金额，支持所有工资与产量分支。
其它语义参数不得与该底料混用。

生产进度 `ScjdQuery` 不传 `groupbyFields`，保留制单、计划、物料、包、颜色、尺码、工序顺序、
扫码员工和部门，包含未扫码工序。请求者的目标分组是取数层的视图参数，不是新的预取粒度。

### 3.2 关键计算规则

| 字段 / 指标 | 规则 | 边界 |
|---|---|---|
| `bs/fhsl/sssl/zpsl/wgs/wts` | 按目标分组 SUM 客户提供的 sum/count 贡献 | 不猜 COUNT 行数或物料/工序 distinct 键；不是独立衣物物理件数 |
| `wcl` | `Σsssl / Σfhsl × 100`；零分母为零；Decimal 两位 ROUND_HALF_UP | 不求和、不平均行级比率 |
| 参与人数 | COUNT DISTINCT 非空员工编号 | 不以报工行数代替 |
| `bgs/bts` | 当前配方不消费、不从明细推断 | 客户没有完整派生规则，纯制单统计不作为支持分组 |
| 订单号 | `jhdh`；空值统一「未关联计划号」 | `dh` 是制单标识，不能冒充计划号 |
| FR-005 / FR-006 / FR-009 主表粒度 | 仅按 `jhdh` 分组；空串、NULL、纯空白统一一个组，其它非空原值保留 | 款号条件只筛选数据，制单、款号、床号、日期和工序不拆分主计划号组 |
| 订单统计组数 / 制单数 | 每个计划号组计 1（包含空值组）；制单数为组内非空 `dh` 去重数 | 空值组不是已确认的计划订单，同制单跨部门不能重复计数 |
| 制单 / 款号 / 床号 / 日期展示 | 制单字段放在组内明细，汇总只呈现整组指标与状态分布 | 不在父级取一个值代表多制单；款式显示名和内部编码来自真实数据，不从提问猜映射 |
| FR-005 / FR-009 状态 | 按制单归集发卡、实收后逐制单判断，再计算已完工、未完工、无法判断制单数 | 无制单标识或无有效发卡时状态不可判断；组内超收不能掩盖其它未完工制单 |
| 进度展示 | 使用受审 `progress_label`；接近 100% 但实收不足仍提示未完工 | 合计达到或超过 100% 也不能据此把子制单全部标为已完工 |
| FR-006 参与人数 | 每计划号组按非空员工去重，主卡按完整获准查询范围独立去重 | 工序人数、款式人数、计划号组人数不能直接相加 |
| FR-006 工序占比 | 同计划号、同业务条件的工序报工工作量 ÷ 发卡数量 | 分母缺失或为零、或指定员工时 `unavailable`；不扩大员工范围补全订单分母；工资报工日期与进度制单日期不同，不能把同月视为同批制单 |
| FR-013 在产制单 | 在获准范围按真实非空制单号计算 | 不显示为计划号订单数量 |
| FR-004 | 先对获准人群排名，再选择本人一行 | 不得先压成本人一行再计算“第 1 名” |

已记录的行合计与 footer 可加性支持贡献列求和，尚未替代客户默认明细到服务端各分组的逐组验收。
同包多工序、多员工的贡献不能随意去重；跨工序产量保持「件·工序」口径注记。
编码与名称同时作为分组字段时共用一个维度；冲突名称、缺列、坏贡献值及不支持分组回退实时。
排序在本地完成，不下发排序参数；排名和展示行均显式指定并列规则。

FR-004 通过安全名册按可信本人编号确认当前小组；多部门绑定不能随意选择一个部门。
名册缺失、组别不唯一或组别不在获准范围时，组内名次与人数明确返回 `unavailable`。
获准工资按员工编号汇总一次；同员工跨部门报工或名称变化不能拆开金额、重复排名或重复返回本人。
组内有工资人员的当前归属若不能唯一确认，组内数据仍明确不可用，不用缺失归属猜测人数。

## 4. 推荐方案设计

### 4.1 执行流程

```text
真实老板 token + AuthorizationService + 租户状态校验
  → 两族默认明细 → 完整性 / footer 门禁 → 日期校验与标准化 → Redis

用户请求 → 能力与租户授权 → 槽位校验 → 公共底料读取
  → 有效范围过滤 → 同时区时间切片 → 业务条件过滤 → 已审查分组视图
  → interaction DuckDB → 相同 recipe → 最终结果 / 卡片 / 导出
```

缓存中宽范围数据来自老板真实授权；提问者范围外的行不会进入其沙箱、产物、审计或 LLM。
老板的最小绑定部门不限制其默认全厂视图，显式请求仍会收窄。普通角色的实时子集不得回填公共键。
交互中的 token 续期不得更换租户或用户；角色或绑定部门变化时，停止在旧范围下业务重试和回填，
由下一交互重新授权后读取，避免将已降级身份的子集写入老板公共底料。

### 4.2 缓存键与值

键为 `fa:{contract}:{metric}:{data}:{tenant_sha256}:{scope_sig}:{domain}:{params_digest}`。
租户使用 SHA-256；`domain=v2_result`、`scope_sig=owner-99`、当前数据版本 `mes-detail-v4`。
参数摘要区分业务源、底料窗口、语义参数及 `default-detail-v4` 粒度。分组、排序、角色及业务收窄
属于读取参数。工资与进度各共享一族底料，但历史预取窗口和当前问题完整窗口可有不同键。

值版本 `v=4`、默认底料粒度 `default-detail-v4`，存列式 JSON 行集、footer、窗口、派生列声明、
生成时间和 `query/precompute` 来源。外层数据命名空间使用 `mes-detail-v4`，日期加工契约由
内层值版本和粒度隔离；旧底料不能作为当前日期来源。
预取租约、完成标记与底料使用相同数据版本命名空间，完成标记只证明本版本的两族底料已写入。
启动预取不能被其它版本的当日完成标记跳过；无需删除旧 Redis 数据，旧键按既有 TTL 到期。
Confidential 业务字段按批准策略原样保存；凭据、密码、签名、accessToken、提示词、最终答案或
ResultTable 永不进入缓存。版本与派生规则变更隔离旧键，组织/授权变更重新计算读取范围。

### 4.3 预取与多租户

沿用一个老板凭据设置，允许单个加密字符串或 JSON 字符串数组；各项都经真实角色、scope、租户
及暂停状态校验。每工厂凌晨 02:00 加确定抖动，启动可预热；两族各一次完整默认明细取数。
跨副本按租户/日期取得 lease，两族真实写入成功才标记当日完成。单工厂或单族失败不会扩大范围，
不会使其它已授权工厂失去预取能力。应用关闭释放专用 adapter。

每轮固定起始工厂时间，租约日期、预热/每日阶段和两族底料窗口使用同一个日期，不因取数跨午夜漂移。

年度老板快照使用独立的有界行数预算，默认 1,000,000 行；普通问题取数仍保留 250,000 行预算。
分页页数沿用既有配置。超过快照预算、返回行数与 total 不一致或缺页时，结果标为不完整，不进入
公共缓存；由获准人员结合一年真实明细容量设置预算，不能通过静默裁剪证明全量。

每轮预取默认限时 600 秒，可由 `FACTORY_AGENT_RESULT_CACHE_PREFETCH_TIMEOUT_SECONDS` 配置。
租约有效期按该上限加安全余量计算；截止时间覆盖完成标记读取、两族取数和回写，取数返回与 JSON
编码后、实际写入前再次检查。超时取消本轮、不写当日完成标记并保留重试状态，拦截超时后继续
回写的常见路径。已完成的一族沿自身 TTL 保存，下一轮继续整刷两族。该机制是客户端有界执行，
不声明 Redis 原子 fencing；任意进程挂起或已发送请求的极端延迟需要服务端 token 条件写才能严格隔离。

### 4.4 加工层与时间锚

工资 `Flag=0` 使用 `inputdate`，`Flag=1` 使用 `check_time`；不同语义隔离。
进度制单日期来自 V2 响应 `rq`，不从 `dh` 编码推断。支持 ISO 日期与合法 ISO 日期时间，取
字段自身的业务日历日期并标准化原 `rq` 为 `YYYY-MM-DD`；不把制单日历日期当作时间点按偏移
换日。缓存与影子实时侧使用同一规则，不新增 `dh_date` 或 `rq_date`，`derived=[]`。
缺失或非法日期拒绝整批缓存，不回退到编号、不丢坏行、不改成零。按制单等视图聚合时，仅在
同组日期完整且唯一时保留 `rq`，日期冲突不任选一个值；不含制单维度的工序视图不补造日期。
`rq` 返回已确认，但作为动态分组字段尚未确认，保持原有审核分组字段。问题窗口仍按部署时区
的包含式日期换算为领域半开区间；这不改变 `rq` 自身业务日期。

实时原生制单分组需要日期而响应没有 `rq` 时，在相同获准范围、窗口及业务条件下有界读取一次
默认明细，再用可信 `rq` 加工视图；额外一次源取数进入调用计量，分页和重试仍另行记录。
默认明细的 `rq` 仍缺失或非法时按 `upstream_invalid` 拒绝，不写缓存、不从编号补造日期。
原生分组正常返回 `rq` 时保持独立原生对照路径；不新增未确认的日期分组字段。

### 4.5 读取路径与保留期

| 问题窗口 | 读取 / 冷态行为 | Redis TTL |
|---|---|---|
| `[今天−365, 昨天]` 内 | 优先历史整窗底料，过滤并切片；其次问题自身快照 | 24 小时，夜间整体刷新 |
| 包含今天 | 同一完整问题窗口的老板明细快照；冷态取数后只对获准范围派发 | 90 秒 |
| 历史预取未覆盖但入口仍允许的窗口 | 问题自身完整快照或正常实时回退 | 24 小时 |
| 安全名册 / 组织资料 | 复用 `identity_org`；冷态按原只读目录来源刷新 | 24 小时 |

回溯边界仍为 365 天，非法或超限输入不能用缓存绕过入口检查。不同窗口快照不拼接；
365 天是数据覆盖范围，不是条目保留期。Redis 失败只回源，不能报告写入成功或阻断回答。

跨日到新一轮预取完成之前，昨天仍未过期的完整底料若完全包含问题窗口，可以继续截取；
优先使用当天新底料。涉及新增边界日、旧窗不覆盖时整窗回源，不拼接昨日快照与当天实时行。

### 4.6 一致性机制

默认 `readwrite`；显式 `off` 只走实时，`read` 只读，`shadow` 命中后仍取实时数据。
完整性证明、已知可加 footer 对账、时间锚和敏感字段门禁在写入之前执行。

shadow 在**同一个 DuckDB 连接**中运行同一受审 recipe 的两套取数结果，比较最终列、逐行结果、
排名、合计、完整性、warnings 及卡片辅助输出。原始行序可以不同，最终行序与排名必须确定。
最终不一致则返回实时、驱逐实际命中的键并告警。取数层行多重集相等不能替代最终 recipe 比对。

进度的实时基线在原生分组保留了本次筛选所需维度时，继续使用客户接口分组结果，只做范围和
业务条件收窄，不重算其分组值。所需员工、物料或其它维度不在原生分组列中时，实时路径使用
获准默认明细先筛后聚合；该范围下的 shadow 核对缓存与新鲜明细的一致性，不能替代客户原生
分组口径的独立对账。真实默认明细与原生分组的等价性仍属于客户环境验收。

### 4.7 可观测性与辅助名册

日志及缓存计数保留命中、未命中、安全键摘要、来源、行数、故障与不一致类别；既有 MES 调用与耗时
记录用于对比。`interaction.result` 可带 `cache_source` 的来源集合与生成时间，不含内部键或身份。
名册安全投影供 FR-011/013 的在册人数和名称解析共用；名册冷态与 token 换取/续期单独解释。
shadow 会主动访问 MES，必须与普通热态样本区分。

### 4.8 订单汇总与组内明细

FR5/FR9 的主结果一行一个计划号组，`sheet_details` 辅助结果保存该组完整制单进度；FR6 主结果
采用相同计划号粒度，`worktype_details` 保存款式/工序报工记录。未关联组保留所有子记录，
不因归为一个组就抹去子制单状态或工序差异。辅助结果与主结果从同一次授权范围、绝对时间及
业务条件的底料计算，明细不逐单请求 MES。

`card.order_groups.version=1` 提供组标识、真实 `kind/plan_code`、汇总、制单状态分布及可分页明细。
空组为 `unlinked`，显示名与查询标识分开；非空计划号原值保留，即使显示名与空组相同也不合并。
父级展示整组指标，制单号、款式、床号和日期只放子表。仅一个组时默认展开；多组默认每页最多
50 组，每个明细默认 10 行。服务端先按组与状态筛选，再切页，并给完整行数、筛选后行数、
当前页、每页数和下一页标记。每页最多 100 行，分页参数必须是有界整数。

组列表分页通过同能力 `drill.group_page/group_page_size/data_snapshot_id`；组内明细通过
`drill.order_view` 选择注册视图、真实组、状态与页码。新一轮请求回传原绝对时间、部门及
订单/款号/计划/物料业务筛选；只有制单视图支持状态筛选。组列表第 2 页及以后、组内明细第
2 页及以后必须携带对应版本摘要。服务端请求模板负责携带这些上下文，中文“未关联计划号”
不能当计划号或制单号传入。制单到包、包到物料工序从卡片 `drill_context` 复制原条件，先按
已审核动作 `clear_fields` 清除失效业务标识，再使用 `bind_from` 绑定真实行标识覆盖相应槽位。
包到工序明确清除作为制单号的 `order_codes`，按真实物料限定；该层不能把制单号当计划号。
动作只能清除订单、款式、计划、物料业务条件，不能清除部门、员工或身份范围。不混合不同
标识，也不继承父层视图或分页版本选择。同能力分页模板保留当前页和当前状态，便于继续翻页。

`card.data_snapshot.id` 为不透明 SHA-256 摘要，绑定配方、能力、角色、租户/员工/部门有效范围、
绝对时间、业务条件、完整获准行集内容及可用的底料生成版本。
它不是认证材料，也不固定未来权限或保证原缓存永久保留。重新执行后版本不匹配，以
`order_view_snapshot_changed` 友好拒绝，要求先刷新汇总，再继续展开；不拼接不同版本的页。
每个新 interaction 都重新授权，未知组、未知视图不回退为宽范围数据。

卡片只投影审核声明列；原始员工标识及未声明数据不出现在订单预览。整组未知列从显示列隐藏，
并在 `unavailable_columns` 提供列元数据；部分行未知显示 `null`，不补零。人数和进度均取
已计算结果，前端不从预览重算。Excel 导出保留完整主汇总和完整明细工作表，分页只影响卡片
预览；指定状态时导出该状态匹配的完整行集。明细工作表前两列固定为“计划号”“关联状态”，
空组与文字同名的真实计划号仍可区分，内部原始组元数据不显示。

FR6 指定员工时工资底料按员工收窄，发卡不作为该员工工作量的全订单分母，工序占比明确不可用；
不能为获得分母扩大有效范围。FR6 及所有工资来源能力不支持物料标识条件，结构化
`material_ids` 在会话服务开始交互前返回 400；进度能力则在获准默认明细先按物料筛选再聚合。
API 请求、响应、失败分类及展示建议统一见
[前端 API 契约 §5.3.2](../api/AI助手前端对接API文档.md#532-订单分组展开与组内分页cardorder_groupsversion1)。

## 5. 验收证据

本地验证使用无网络合成数据，覆盖全部 FR 和下钻、真实范围收窄、拒绝零业务调用、完整排名人群、
同包多贡献、未扫码行、坏缓存、写失败、跨日、当前窗口、多租户生产者及最终 shadow 不一致回退。
工程检查和真实环境验收是不同证据，不由某个模式开关或缓存键存在自动判定需求完成。

仍需在获准环境完成：各真实角色对照、默认明细到服务端列表/包/工序逐组等价、V1 锚点对账、
历史倒补稳定性、一年明细的响应/Redis 体积与内存峰值，以及按 FR/角色/窗口的命中率和耗时基线。
本轮没有执行客户访问，不给这些项目打完成标记，也不引用旧聚合底料体积代表一年明细容量。

```text
python scripts/diagnose_cache_prefill.py --help
python scripts/verify_result_cache_read.py --help

```

`--help` 只解析参数，不加载应用或 `.env`。正常预取诊断会访问客户并写 Redis；`--dry-run` 只取数
和检查门禁，`--reuse-fetch` 只验证当前 Redis 快照。读取诊断不取业务明细，但真实身份授权仍可能

## 附录 A · 当前明细加工事实与边界

### A.4 空部门与未扫码行

生产进度 V2 契约 §6.1 明确默认明细包含未扫码工序，员工编号/姓名可为空，已扫码工序贡献为零。
空部门不能证明属于任何指定部门；老板获准全厂视图保留这些行，部门视图排除这些行。
本条是范围派发规则，不据此推断未扫码工序的物理数量或客户的包完成算法。

### A.5 日期锚

工资产量 V2 的 `Flag=0/1` 分别使用报工日期 `inputdate` 和审核时间 `check_time`。
进度接口窗口按真实响应 `rq` 的流程卡制单业务日期选择，标准化日期直接写回 `rq`。
ISO 日期时间仅取经过验证的字段日期部分，不按偏移换日。`dh` 只用于标识，不参与日期推断；
没有独立派生日期列。日期缺失、格式非法或缓存与实时加工不一致时拒绝缓存并回源；不能通过
跳过坏行缩小结果后宣称完整，实时数据仍无法验证时明确不可用或失败。
客户各角色与各服务端分组的逐组对账、历史倒补稳定性仍按 §5 验收。

## 附录 F · 当前缓存协议

### F.1 值结构

`v=4` 的列式 JSON 保存 `api`、`window`、归一化语义参数、`columns`、`rows`、`footer`、
`derived`、`generated_at` 和 `source`。公共值粒度为默认明细；生成来源限定 `query/precompute`。
结构、窗口、语义参数、列宽及日期锚不匹配时不使用该值。进度原 `rq` 标准化后随明细持久化，角色结果和
最终卡片不在值中。具体序列化实现位于 `data_api/result_cache.py`。

两族的键形状一致，参数摘要分别包含 `GongziClQuery` 或 `ScjdQuery`：

```text
fa:mes-contract-v2:metric-registry-v1:mes-detail-v4:{tenant_sha256}:owner-99:v2_result:{params_digest}
```

以下是虚构数据的可读示例，仅展示部分业务列；实际行集保留所有受审使用字段。Redis 中 value
为紧凑 JSON 字节串，`columns` 的顺序对应每行数组的值顺序。

HTTP 分页和重试次数由既有 MES 计量另行记录，不与资源取数次数混为一个性能指标。

### F.2 TTL

按 §4.5 执行已批准的 24 小时历史/回填、90 秒未结算完整窗口和 24 小时基础资料保留期。
每天整刷不代表条目永久保留，365 天覆盖范围也不代表 365 天保留期。

### F.3 参数归一化

底料键携带默认明细粒度和真正影响底料的语义参数，`Type` 取值排序去重。
分组、排序和提问者业务收窄条件只控制读取视图，不拆出重复底料键。
客户端输入不能覆盖租户、角色、身份或已授权范围。归一化不能用来合并不同审核/来源口径。
