## 1. 背景与目标

前端完成了一轮结果卡片原型设计（工资 / 进度 / 产量三个主题），相较现行卡片有三个升级点：

1. **综合看板形态**：一张卡片内同时呈现 KPI 指标区（如工资总额 / 人均工资 / 在册人数）、
   图表区（如按日产量柱状图）和排名列表区（如车间产量排名）；
2. **层级下钻**：卡片行可点击，逐级下钻（车间 → 组 → 成员 → 个人工资条）；
3. **分页/加载更多提示**：前端样例已定义 `page / page_size / has_more` 三字段约定（可选增强）。

本文档回答四个问题：现有能力返回的数据是否支持、卡片协议改造量有多大、下钻如何触发、
结果是否需要缓存；并给出分阶段实现清单。

## 2. 现状与差距分析

### 2.1 三张原型卡 × 现有能力数据支持对照

| 原型卡区块 | 数据来源（现状） | 支持情况 |
| --- | --- | --- |
| **全厂工资总览（图3）KPI**：工资总额 / 人均工资 / 在册人数 | `fr011_factory_payroll_stats`：`GongziJeOrderQuery`（按 dept 汇总应发）+ `EmployeeQuery`（在册人数）+ `DeptQuery`（部门名）。工资总额=Σgross_total ✓；在册人数=Σheadcount ✓；**全厂人均工资=Σgross÷Σheadcount，现有 card 只支持对列 SUM，无法直接给** ⚠ | 基本支持，缺「全厂人均工资」单值口径（见 4.2 aux 输出） |
| **全厂工资总览车间列表**：车间名 / 人数·占比 / 应发合计 | `fr011` 主表即部门粒度（dept_name/gross_total/headcount/avg_wage），占比可由前端按 Σ 计算 | **完全支持**，无需后端改动 |
| **工资排名（图1）**：名次 / 姓名 / 小组 / 计件 / 金额 | `fr008_payroll_ranking`：uid/uname/dept/package_count/gross/rank_position/group_rank，服务端已排序，`group_by: dept` 分组 | **完全支持**（进度条=相对最大值比例，前端渲染层实现） |
| **点成员查看工资条** | `fr012_employee_payroll`（任一员工工资查询，`GongziMxQuery` 按目标 uid 取明细合计） | 支持，**但 fr012 按矩阵仅老板可用**（见 D-5） |
| **全厂产量总览（图2）KPI**：总产量 / 人均月产 | `YskQuery`（Σsl）÷ `EmployeeQuery`（在册人数） | 支持，属新计算口径，需新能力承载 |
| **全厂产量总览 KPI**：在产订单 N 单 | 无现行口径。候选：统计窗内 `ScjdQuery` 包完工率（wcl）<100% 的制单（dh）去重数 | **缺口，需拍板口径（D-2）** |
| **产量日/周柱状图** | `YskQuery` 行内含 `rq`（报工日期，`output.yaml` fr001 已按 rq 分组），同一次取数即可按日聚合 | 数据支持；**卡片协议无 chart 区块，需新增（4.1）** |
| **车间产量排名 + 点车间下钻** | `fr007_workshop_output_comparison`（rank/dept_name/output_qty/participant_count/per_capita） | 列表支持；下钻见 4.4 |
| **车间 → 组 → 成员三层** | **已拍板（2026-09-16）：车间=组=部门，三者同义**，客户部门即单层；下钻链为「部门 → 成员」两层，原型中的三层文案按两层理解 | 无缺口；原型的「车间→组」为同一层级的重复表述，前端文案需同步修正 |

**结论：数据面没有硬缺口**——三个缺口里，两个是协议/内核形态问题（chart 区、单值 KPI），
一个是口径待拍板（在产订单）；部门层级是客户事实待确认，不是我们代码能解决的。

### 2.2 卡片协议差距（对照前端《最大全集》样例）

| 前端样例字段 | 后端现状 | 差距 |
| --- | --- | --- |
| `page / page_size / has_more` | 只发 `truncated` / `preview_max_rows` | 小：`build_card` 派生下发即可（page 恒 1） |
| `groups[].name`（组显示名） | 只有 `group`（编号） | 小：groups 项补 name（需在 rows 或 DeptQuery 结果中取） |
| chart（柱状图序列） | **协议不存在** | 中：新增可选 `card.chart` 区块 + recipe 辅助输出机制 |
| 全厂级单值 KPI（人均工资等不可 SUM 指标） | metrics 取值 = totals SUM 或单行值 | 中：recipe 辅助输出机制（4.2） |
| 下钻入口声明 | 无（前端目前按 capability_id 硬约定） | 小（可选）：卡片下发 `actions` 提示可点击（D-4） |

### 2.3 与「三层下钻」现行模式的一致性

进度族三层下钻已拍板：**每层是一次独立问答轮次**（不是同一次 SSE 塞三层）。
工资/产量的层级下钻沿用同一模式，前端交互心智一致，后端不需要新的会话内状态。

## 4. 实现方案

### 4.1 卡片协议增量（全部向后兼容，缺席即现行为）

```json
{
  "kind": "ranking",
  "...": "现行字段不变",
  "metrics": [ { "label": "人均工资", "unit": "元", "value": "3016" } ],
  "chart": {
    "type": "bar",
    "unit": "件",
    "granularity": "day",
    "points": [
      { "label": "09-08", "value": "2460" },
      { "label": "09-09", "value": "2670" }
    ]
  },
  "actions": [
    { "type": "drill", "label": "查看该车间工资", "capability_id": "fr008_payroll_ranking",
      "bind_from": { "dept_ids": "dept" } }
  ]
}
```

- `card.chart`：可选，`points[]` 由服务端排好序；无数据时整个区块缺席（不下发空数组）。
  本期 `type` 仅 `"bar"`（枚举位预留）；`granularity` 取 `day` / `week`：**点数上限 62，
  统计窗超限由后端在 aux 里自动降为周粒度**（前端零聚合逻辑）；`label` 为原始日期
  字符串（日粒度 `MM-DD`、周粒度 `MM-DD` 为周起始日），本地化展示由前端负责。
- `card.actions[]`：可选，**卡片级**下钻声明（不做行级内嵌，避免行数据重复膨胀）。
  `bind_from` 为「槽位键 → 列名」映射（如 `dept_ids ← dept` 列、`employee_uid ← uid` 列）：
  前端点击某行时，从该行数据取对应列值填入槽位，组装 `drill` 载荷（见 §4.4）。
  键名与 `ALLOWED_SLOT_NAMES` 对齐；actions 是纯提示性字段，前端忽略它零行为变化。
- `card.table` 增发 `page=1 / page_size=<preview_max_rows> / has_more=<truncated>`（分页三字段一起发，满足前端「要么都不发要么都发」校验）。
- `groups[]` 项补可选 `name`（部门显示名）。

### 4.2 recipe 辅助输出机制（aux 输出）

现状：一个 capability 一次运行只产一个 `ResultTable` + 一张卡；卡上的数字只能来自
主表列的 SUM 或单行值，因此「全厂人均工资」这类**不可 SUM 的单值指标**和**日聚合序列**
放不进卡片。

方案：recipe 的 compute 段允许声明**辅助输出**（不进主表、不进导出，只进卡片）：

```yaml
compute: |
  ...（主查询：部门聚合，现行不变）
aux_outputs:
  - aux_id: daily_series
    into: chart            # 进 card.chart
    compute: |
      SELECT rq AS label, CAST(SUM(...) AS VARCHAR) AS value
      FROM fetch_ysk GROUP BY rq ORDER BY rq
  - aux_id: factory_kpi
    into: metrics          # 合并进 card.metrics（不可 SUM 的单值口径）
    compute: |
      SELECT CAST(ROUND(SUM(g)/NULLIF(SUM(h),0),2) AS VARCHAR) AS overall_avg_wage, ...
```

内核改动点（`execution/kernel.py`）：`_run_compute_steps` 收集 aux 结果（小行数，上限
如 62 点/若干 KPI），`_build_card` / `ports/card.py::build_card` 接收并拼入 payload；
aux 输出同样受审计与脱敏约束（sensitive 字段不进卡片）。主表、导出文件、名次逻辑零变化。

### 4.3 三个卡片的落地形态

| 卡片 | 承载能力 | 后端改动 |
| --- | --- | --- |
| 全厂工资总览 | `fr011`（不新增能力） | aux 输出全厂 KPI（工资总额/人均工资/在册人数）；`actions` 下钻声明；groups 补 name |
| 计件工资排名 | `fr008`（不新增能力） | 分页三字段；`actions`（点成员 → fr012，**01/02/99 三角色均下发**，D-5 拍板）；前端渲染升级（进度条）为主 |
| 全厂产量总览 | **新增 `fr013_factory_output_dashboard`**（仅老板） | `YskQuery + DeptQuery + ScjdQuery`：主表=车间排名（复用 fr007 口径），aux=KPI（总产量/在产订单（D-2 口径：ScjdQuery wcl<100% 制单去重）/人均月产）+ 日序列 chart；`actions` 下钻声明 |

产量总览独立成能力而非改造 fr007 的原因：fr007 的名次列带「N=1 置 unavailable」分支与
对比语义，看板卡需要恒定排名列表 + KPI + chart 三区块，混在一起会破坏 fr007 现有契约。

### 4.4 下钻触发机制：不是分页，是新的一轮问答

- **分页** = 同一结果集内翻页（`artifact rows` 级别），**下钻** = 带 收窄条件的新查询。
  两者正交，互不替代。
- 触发流程（方案 B，结构化通道）：
  1. 前端点击卡片行/组 → 按 `card.actions` 组装 `drill` 载荷；
  2. `POST /v1/sessions/{sid}/interactions` 请求体新增**可选**字段：
     `{"text": "<用户可见的一句话，如「查看后道车间工资」>", "drill": {"capability_id": "...", "slots": {"dept_ids": ["001"]}}}`；
  3. 服务端：身份/角色鉴权照旧 → 校 drill 能力在矩阵内、槽位键在白名单、值只**收窄**
     （部门必须在 DataScope 内，员工必须经 EmployeeQuery 解析，与 fr012 现行门禁一致）→
     注入槽位后直接进入执行，跳过 LLM 意图路由；
  4. 下钻轮次照常走完整事件流、持久化、审计与计量——历史回看、收藏复问、导出全部天然兼容。
- `drill` 缺席时行为与现在完全一致（纯文本走 LLM 路由），方案 A 作为兜底始终可用。
- 安全不变量：身份永不来自请求体（`drill` 只是业务槽位，同现行 `text` 待遇）；任何
  drill 槽位不能放大 DataScope（服务端二次校验，纵深防御）。

### 4.5 缓存策略：本期不新增结果缓存

结论：**每次下钻都是一次全新的鉴权 + 取数 + 计算，不做跨请求结果缓存**。理由：

1. MES 行级过滤按调用者角色生效，缓存复用有权限扩散与数据过期双重风险，与
   「授权先于取数」的架构不变量相抵触；
2. 取数成本已由两层分页探针（首页 20000 → total 超页即 50000/页重走）控制，单轮秒级；
3. 历史卡片回看不依赖缓存：`card` 已随 `result_table` 消息持久化（实时/重放/历史三路一致），
   刷新后从 messages 渲染，点击下钻再发新轮次即可；
4. 收藏/复问机制已可按需重新生成。

可选后续优化（不进本期）：同会话同租户、短 TTL（如 60s）的 MES 原始响应缓存，
仅在实测下钻并发压力成为问题后再立项。

### 4.6 分页

- 本期只做**协议对齐**：后端下发 `page / page_size / has_more`（从 `truncated` 派生，
  成本极低），前端「加载更多」提示逻辑统一。
- 真正的翻页数据接口（`GET /v1/artifacts/{artifact_id}/rows?page=&page_size=`，响应复用
  CardTable 结构）需要结构化行存储——当前导出只有 xlsx 落盘，另立 Story，不阻塞本次卡片改造。
