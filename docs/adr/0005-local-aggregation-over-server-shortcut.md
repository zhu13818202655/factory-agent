# ADR-0005：MES 数据获取以本地加工为主，聚合短路不实现

- 状态：Accepted（2026-08-25 经客户答复确认，不再是临时决定）
- 日期：2026-08-24，2026-08-25 修订
- 所有者：项目维护者
- 关联：CQ-09、CQ-15（均已答复）、M13、M16、Story 3、Story 5

## 1. 背景

CQ-09 与 CQ-15 向客户询问两件事：

- 客户 MES 是否提供服务端聚合接口；
- 平台是否可以自主组合多个基础 API 完成跨 API JOIN、GROUP BY 和 RANK。

客户已于 2026-08-25 答复：

- **M16**：明确允许智能体平台自主组合、关联、分析多个 MES 只读 API；车间对比、趋势、
  达成率等聚合指标由我方拉明细自行计算。
- 当前提供的 27 个接口**全部为只读查询接口**，其中仅 `GongziMxQuery`（`scheme=hz`）、
  `HuohaoWtCLQuery`、`GongziJeOrderQuery` 提供有限的单接口维度汇总与 `footer` 合计，
  不存在跨接口的服务端聚合能力。

## 2. 决策

1. **本地加工为主**：跨 API JOIN、GROUP BY 和 RANK 一律在 interaction 级内存 DuckDB 沙箱中
   完成。这是唯一被支持的执行路径。
2. **使用客户已有的单接口汇总**：`scheme=hz`、`queryFooter` 与 `footer` 合计属于接口自身
   能力，可直接使用，且应作为本地合计的**独立对账来源**；二者不一致时产生结构化
   对账失败，不取其一。
3. **不实现跨接口聚合短路**：客户不提供此类接口，Catalog 不登记虚构的聚合型 operation。
4. **Adapter 边界保持不变**：若客户后续新增聚合接口，差异仍然只允许被 Adapter 消化，
   必须返回等价的领域对象。
5. **预算口径**：本地拉全意味着分页预算必须覆盖明细行数。客户未声明分页上限与限流
   策略，`size` 与最大页数为占位配置，Story 10 联调时核对。

## 3. 后果

- 正面：Story 6~7 可以基于单一执行路径注册配方；内核复杂度最低；沙箱逃逸面最小。
- 风险：`WorktypeProgressQuery` 必须逐物料编号查询，FR-009 全厂进度总览存在 N+1，
  需靠预算与分批控制（Story 7 风险项）。
- 风险：客户 MES 明细数据量远超预期时，本地拉全可能成为瓶颈；K3 已确认性能上限
  本期不作为阻塞项，由 Story 8 测量、Story 10 联调验证。

## 4. 关联影响

- Story 3：清单中“支持聚合接口短路形态”标记为本决策关闭。
- Story 5：Catalog 重建时将 `scheme`/`queryFooter` 登记为接口参数，不视为聚合型 operation。
- Story 6：三方对账（明细合计 / 本地汇总 / `footer`）作为通用工具实现。
- Story 10：双跑时必须重新核对分页上限与预算配置。
