# ADR-0005：MES 数据获取以本地加工为主，聚合短路不实现

- 状态：Accepted（2026-08-25 经客户答复确认；口径来源统一为
  `docs/product/需求及方案整理.md`「客户确认结论」）
- 日期：2026-08-24，2026-08-25 修订
- 所有者：项目维护者
- 关联：`docs/product/需求及方案整理.md`「客户确认结论」（客户答复记录）

## 1. 背景

本决策由两项向客户确认的事实驱动：

- 客户 MES 是否提供服务端聚合接口；
- 平台是否可以自主组合多个基础 API 完成跨 API JOIN、GROUP BY 和 RANK。

客户已于 2026-08-25 答复：允许智能体平台自主组合、关联、分析多个 MES 只读 API；车间对比、趋势、
达成率等聚合指标由我方拉明细自行计算。

- 当前提供的 27 个接口**全部为只读查询接口**，其中仅 `GongziMxQuery`（`scheme=hz`）、
  `HuohaoWtCLQuery`、`GongziJeOrderQuery` 提供有限的单接口维度汇总与 `footer` 合计，
  不存在跨接口的服务端聚合能力。

## 2. 决策

1. **本地加工为主**：跨 API JOIN、GROUP BY 和 RANK 一律在 interaction 级内存 DuckDB 沙箱中
   完成。这是唯一被支持的执行路径。
2. **使用客户已有的单接口汇总**：`scheme=hz`、`queryFooter` 与 `footer` 合计属于接口自身
   能力，可直接使用，且应作为本地合计的**独立对账来源**；二者不一致时产生结构化
   对账失败，不取其一。
3. **不实现跨接口聚合短路**：客户不提供此类接口，Catalog 不登记虚构的聚合型 operation。
4. **Adapter 边界保持不变**：若客户后续新增聚合接口，差异仍然只允许被 Adapter 消化，
   必须返回等价的领域对象。
5. **预算口径**：本地拉全意味着分页预算必须覆盖明细行数。客户未声明分页上限与限流
   策略，`size` 与最大页数为占位配置，客户真实环境联调时核对。

## 3. 后果

- 正面：全部能力配方注册在单一执行路径上；内核复杂度最低；沙箱逃逸面最小。
- 风险：`WorktypeProgressQuery` 必须逐物料编号查询，FR-009 全厂进度总览存在 N+1，
  需靠预算与分批控制。
- 风险：客户 MES 明细数据量远超预期时，本地拉全可能成为瓶颈；客户答复中性能上限
  本期不作为阻塞项（见 `docs/product/需求及方案整理.md`「客户确认结论」），由性能测量
  与客户真实环境联调验证。

## 4. 关联影响

- `scheme`/`queryFooter` 已登记为 Catalog 接口参数，不作为聚合型 operation 注册。
- 三方对账（明细合计 / 本地汇总 / `footer`）作为通用工具实现。
- 客户真实环境双跑时必须重新核对分页上限与预算配置。
